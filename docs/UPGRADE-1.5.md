# 1.5：状态为什么更新、什么时候保持

本轮优先完成一条可核对的路径：读取真实 RTL → 声明状态更新规则 → 解释图与条件表 → 点击回查源码 → 生成监视器检查实际 RTL。没有把新布局启发式当作硬件理解。

## 可以直接使用的变化

- **状态更新表**：点击有规则的寄存状态，查看复位、顺序条件、写入值与默认保持。第一条成立的条件优先；右值来自有效沿前。
- **明确的连线角色**：更新规则区分写入值、更新条件、复位与多角色来源。旧模型仍显示输入集合未知，不从信号名字推断。
- **按问题追踪**：“数据从哪里来”与“什么时候更新”突出不同依赖，默认两层、上游状态停止。背景连接保留，支持继续追踪及返回。
- **有限结构标签**：单分支规则显示条件装载寄存器，多分支显示优先级更新寄存器；模型和源码可追溯，不宣称识别了完整流水线或仲裁器。
- **同源检查器**：新增 state_transition 义务，复用 checks / verify / assurance。模型的组合 AST 内联为期望表达式，显式映射实际输入/状态；检查器变更和模型变更会使旧生成物失效。
- **skill 方法**：强调同时条件的优先级、不同状态不同更新条件，以及能区分正确与错误结果的保持测试；详细规则按需阅读，不增加强制问卷或新审批步骤。

## 支持边界

`register.update` 为可选 IR 3 字段；旧模型不自动添加，不改变既有 fixture hash。支持整向量、单有效沿、明确优先级的同步更新；复位可显式为 null，否则要求同域同步、极性与作用域一致。部分位写入、多过程驱动、数组存储与异步过程继续保留原输入集合及缺口。直接 RTL/Yosys 自动提取更新规则尚未实现，本轮示例经过源码逐行整理。

监视器在有效沿采样，在相反沿检查。它要求每个声明分支、复位（若有）、默认保持都被触发，不覆盖全部沿间瞬态或任意输入序列。分支计数不证明刺激足够：实测发现相同数据的重复写入会掩盖错误，因此示例让新输入与被阻塞的旧输出不同，并用故障注入确认检查能发现错误。

映射仍由作者核对，组合表达式不能通过“映射到同名 RTL 组合线”跳过模型预期。检查器只证明实际运行范围内的状态关系；批准、partial、源码新鲜度和完整行为证明保持独立。旧图与旧 HTML 仍是原版本快照。
