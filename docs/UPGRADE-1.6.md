# 1.6：检查依据、覆盖缺口与可复现回归

本轮对照 v1.5 技术评审和实际源码，优先修复会让用户误判验证结果的问题。图、状态规则和合同继续共用唯一模型；没有另造一份可编辑意图模型，也没有把长篇路线图塞进 skill。

## 评审中采纳了什么

| 评审意见 | 核对结果与本轮实现 |
|---|---|
| 无条件更新也强制覆盖保持 | 确认是 stateChecks 的实际缺陷。常量规则证明不可达的路径单列，不再强求命中 |
| 分支分别执行过不代表验证了优先级 | 增加显式 priorityPairs；要求高优先级被选中、条件同时成立且右值不同 |
| 从 RTL 抄出相同模型可能自洽但违背需求 | 验证保存运行前批准依据；页面区分还原一致性、未批准设计、已批准设计声明，并列出未关联义务的需求 |
| 本机保存的 PASS 不能代替持续回归 | 新增固定工具版本及下载摘要的 GitHub Actions；执行既有检查和本轮真实 RTL 反例 |
| 缺少任意 RTL 提取、完整类型语义和复杂图基准 | 问题成立，但需要独立前端/类型设计和人工读图样本，列为后续工作；本轮不声称完成 |

## 状态覆盖变得可解释

生成检查器时就确定覆盖目标；运行记录给出复位、分支、保持、完成比较及已声明竞争的计数。网页“行为约定 → 核验状态”可按需展开，并在覆盖不足时直接给出下一步激励建议。CLI 的 nextSteps 返回相同建议，不用翻仿真日志猜原因。建议不证明场景可达，也不改写 TB。

- **已命中**：本次仿真确实触发。
- **未命中**：仍需激励；返回 coverage_incomplete，区别于实际状态不符导致的运行失败。同一次验证另有检查失败时，保留失败结论，不因检查顺序被降级为覆盖不足。
- **不可达**：只依据字面常量证明。常量 0 分支、被更早常量 1 屏蔽的分支、存在常量 1 更新时的默认保持都有具体原因。
- **未知**：覆盖记录缺失或不能核对；不能算通过。

这不是 SAT/形式可达性分析。`enable` 即使在本次 TB 中一直为 1，也不能据此免除保持覆盖；非字面常量表达式不作静态不可达推断。改变旧值的写入和实际状态变化是诊断计数，不代表自动做过故障检测。

需要检查关键优先级竞争时，在原有 state_transition 义务中添加：

```json
"priorityPairs": [{"higher":"cancel","lower":"load"}]
```

两个 ID 必须对应更新规则中的分支，并按优先顺序排列。分别执行、同时写相同值、被其他更早分支屏蔽，均不能冒充已检查这次竞争。未声明的竞争不在覆盖承诺内；旧模型不自动增加字段或改变 hash。

## 不再把还原一致性说成需求验收

`checks.json` 带有关联需求的文字、验收条件摘要、义务绑定指纹及生成源码摘要。`run.json` 保存本次模型、输入、工具、覆盖结果与**执行前**的本地批准记录摘要。`assurance` 同时呈现这些联系及没有义务的需求。

已有的 as_built 示例仍保持 partial。它的 x+3 RTL 与 x+3 规则可以通过，但即使贴上“应加五”的 requirementId，也只能得到还原一致性证据。新增回归先固定并批准加五设计规则，再检查加三 RTL，确实失败；修正为加五后才通过。需求文字与规则是否对应仍由审阅负责，工具没有自然语言等价证明。

事后批准不能提升旧的草稿运行；需求变化使批准和旧检查器过期。本地 reviewer 记录仍未认证身份；保存批准快照也不是受保护的外部审批。

## 日常使用不增加新流程

继续用 `checks → verify → assurance`。优先看检查依据与具体覆盖缺口，再补最有区分力的激励。关键竞争才声明 priorityPairs，不给每个模块机械堆断言。skill 的详细说明仍按需读取 [状态更新](../.agents/skills/rtl-architect/references/state-updates.md) 和 [验证](../.agents/skills/rtl-architect/references/verification.md)。

升级后，旧生成物与当前生成规则不匹配时会明确失效。按已有方式生成到新目录并更新验证清单输入，不修改真实项目模型、审批或历史运行来迁就新工具。

## 可复现检查

[CI 配置](../.github/workflows/ci.yml) 固定 Node 24.18.1、npm 11.6.2，使用 [OSS CAD Suite 2026-09-09](https://github.com/YosysHQ/oss-cad-suite-build/releases/tag/2026-09-09) 的 Linux x64 发布包及 SHA-256。工作流 action 引用固定提交，符合 [GitHub 的固定版本建议](https://docs.github.com/en/actions/reference/security/secure-use#using-third-party-actions)。Ubuntu 24.04 runner、系统编译器等实际版本记录到每次日志；这不是完整机器镜像冻结。

顺序执行 `npm ci`、`build`、`check`、`rtl:test`、`check:workflow`，失败保留日志，不部署或发布。新增 `check:reliability` 包含无条件计数、未命中保持、两种无区分力的竞争场景、错误优先级、独立需求反例、事后批准及需求修改失效。既有数据、复位、保持等故障回归继续执行。

远端 CI 是否通过以 GitHub 本次运行记录为准；加入配置不等于已经运行。当前实际执行结果、截图和限制见 [VALIDATION](../VALIDATION.md)。

## 下一阶段边界

有限 RTL 自动提取应从成熟前端的明确子集开始，保留观察快照、来源和不支持项，再与批准模型比较，不能用正则猜 always_ff。比较/移位/有符号表达式需要统一类型规则后扩展。复杂布局应先固定 FIFO、仲裁、共享 RAM、反馈等阅读基准，再优化并进行人工读图；间距数字不能替代理解度验收。本轮没有改动这些语义或布局策略。
