# 把讨论、计算和验证接回设计

用户不必重述前一次会话。先 `resume --workspace <项目> --json` 读取目标、下一步、未解决讨论、候选状态和运行记录，再按对象获取 `context --module <id>`。服务不可用时用 `resume --offline` 只读；正式操作前重新在线核对。

## 打开与续接

`rtlarch open --workspace <项目>` 核对页面构建、工作区与服务身份，按需构建并尝试打开浏览器；失败返回可复制的 reviewUrl。机器调用加 `--json`，只返回地址。无模型时显式 `open --init` 创建时钟、复位和职责尚未定义的草稿；不会覆盖已有模型。

旧服务仍在运行时，先提醒保存页面中未发送的输入，再使用 `open --restart` 重启这一工作区。不得为维护工具顺手重启其他项目。历史离线 HTML 是快照，不能通过刷新变成最新设计。

## 图中问题 → 答复 → 用户核对

用户可在网页选择模块或连接，通过“讨论与继续”保存问题。页面不运行模型：回到 Codex 后读取 resume/context，处理问题并保存答复。消息与架构版本、对象和候选绑定；缺失对象、过期候选保留历史，不悄悄改绑。

Agent 使用结构化动作文件，通过同一服务写入；先 `workbench --workspace <项目> --json` 取得 **workbenchHash**。讨论版本与 modelHash 不同，不能混用。完整格式以 `schema workAction` 为准：

```json
{
  "baseHash": "<当前 workbenchHash>",
  "action": {
    "kind": "reply",
    "threadId": "<问题 id>",
    "author": "agent",
    "modelHash": "<当前已保存模型 hash>",
    "text": "说明结论、依据、成立条件和待核对项；必要时沿一笔事务解释。",
    "proposalId": "<可选：已登记且未过期的候选 id>"
  }
}
```

```bash
rtlarch workbench proposals/reply.json --workspace <项目> --json
```

省略不用的 proposalId，不填占位符。答复使问题变为“已答复”，用户核对后才标为“已解决”；不要替用户批量关闭问题。改变结构时先 preview/propose，再把候选关联到答复；讨论不会提交模型或批准架构。

告一段落，保存一个简短 checkpoint：`kind=checkpoint`，`intent` 写本轮目标，`nextStep` 写下次可执行的一步，`target` 包含 modelHash、可选 moduleId/connectionIds/proposalId。候选目标必须使用候选 hash 和登记 id；当前模型使用当前 hash。不要把整段聊天复制进工作记录。

冲突返回 WORKBENCH_CONFLICT：保留未发文字，重读最新记录后合并；不凭旧 baseHash 重试覆盖。候选冲突则保留原提案、重新分析差异。

## 可重复计算的方案预算

先选一个足以改变架构选择的瓶颈，固定配置、工作量与假设，比较 2–6 个方案。网页有两方案表单，CLI 支持完整格式：`schema study` → `study budget.json --json`；保存用 workbench 的 `kind=study`。每份保存记录 ID 唯一，修订另存，不能覆盖旧假设。

每个方案输入：并行单元数、每项运算数、每次运算的资源占用周期、不可重叠开销；可选存储深度/位宽/副本数、每项读写次数和**总独立**读写端口；可选每周期持续产生量、最大停顿、在途量、容量。

共同计算器给出：

- 计算服务量 / 并行单元数，与存储服务量 / 端口数取最大，得到平均服务间隔下界，允许分数。
- 总工作量的计算/存储服务量取最大、向上取整，加不可重叠开销，得到总周期下界。
- 存储位数 = 深度 × 位宽 × 副本；停顿缓存需求 = 持续产生量 × 停顿周期 + 在途量。

模型假设运算可独立分配、读写端口独立、各阶段重叠；存储副本不自动增加可用端口。共享单端口、递推依赖、银行冲突、复用仲裁或启动/排空不满足时，拆成适用阶段或保留未知，不能把下界当成可达到的周期、II、面积或 Fmax。初始表单数字是填写起点，必须按实际设计修订。

关联 runIds 只接受当前模型、输入匹配、通过且覆盖预算模块的运行。它们是检查证据，**不自动证明某个预算数值或 A/B 实现已实测**。报告实际周期/面积时给出对应实现、配置、日志指标及提取依据。结构 A/B 继续用 compare/draft，不把预算选项当成已实现电路。

## 显式执行验证

复用工程已有自检；先读命令和输入，确定运行属于用户已授权任务。不要执行未知下载/发布脚本。`rtlarch verify profile.json --workspace <项目> --json` 使用明确 argv、无隐式 shell；只由 CLI 显式执行，网页没有任意命令执行入口。准确 schema：`schema verification`。

清单指定 stage、moduleIds、完整 inputs（包括脚本、include、配置、ROM/向量等）、timeoutMs、commands 和 checks。program/args 中 `{runDir}` 替换为本次新的绝对目录；相对输入路径和命令 cwd 为 workspace。工具不自动发现传递依赖。

checks 可为 exit_code、contains（独立报告含明确成功标志）、junit（至少一个实际 testcase，失败/错误/跳过均不判通过）。优先工程自检及结构化报告；只看退出码不足以证明行为正确。命令失败、超时、输出超限、输入/模型运行中变化、空报告均不通过。失败也保存本次日志。

`evidence/runs/<id>/run.json` 保存输入摘要、清单、命令、探测到的工具版本、报告摘要与结果；每次新目录，不能把旧 PASS 日志拼进新结果。`runs` 或网页会重新核对输入与报告；变化时显示失效。未提供 versionArgs 的工具版本为 unknown。profile 必须自行声明全部影响结果的环境与依赖；这些记录不是签名、依赖自动发现或等价证明。

运行结果不自动写进 IR provenance，不自动确认架构。需要正式声明时，经提案加入对应来源、阶段、输入摘要和本次报告。

## 只复核受影响范围

新确认记录包含模块子树、相关连接、局部驱动、相邻合同、父层环境、相关需求，以及全局时钟/复位和来源的指纹。无变化模块保留确认；受影响模块列出复核原因。空 moduleIds 的需求视为全局。来源缺乏精确影响边界时保守扩大范围。

旧确认没有依赖指纹，模型变更后按旧方式重新确认。整体批准与导出合同仍绑定完整当前模型，不能用保留的局部确认跳过整体批准。讨论、预算、布局和续接记录不改变模型 hash。

1.3 增加 artifact（保存本次产物摘要）与 obligations（关联实际触发的合同监视器）检查。使用范围、输入闭包声明及独立状态见 [架构可验证](verification.md)。runs 的 fresh 只表示已声明输入及模型仍匹配，不能证明依赖清单完整。
