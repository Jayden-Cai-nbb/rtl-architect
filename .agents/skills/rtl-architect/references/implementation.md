# 按批准合同实现 RTL

现状还原（as_built）和不完整投影不能用于实现交接；先形成范围明确、覆盖已审阅的 design 提案并由人批准。不能通过删来源或仅改完整性标记解除限制。

运行 `rtlarch handoff <moduleId> --workspace <项目> --json`。读取当前 module、interfaces、connections、requirements、clocks、resets 和 modelHash；handoff 会检查确认状态和导出合同内容，不需要手工信任旧 generated 文件。

开始实现前，将模块 ID 与 modelHash 记入本次实现记录。按接口、参数、复位、背压、延迟条件及不变量实现；测试用验收条件判断正确性，不以结构检查结果替代仿真。

先读取本项目当前编码规范和邻近 RTL 的实际约定，不把反馈项目的命名、注释密度、复位或语言版本推广为通用规则。先列出模块持有的状态、更新条件和组合输出，再选择 RTL 写法。逐项核对定宽运算、符号扩展、截断、计数边界、RAM 读写冲突、复位覆盖和参数极值；没有相应行为的模块不机械套用清单。禁止用默认零值掩盖尚未决定的协议行为。

按 [时序方法](timing.md) 将批准合同落实到寄存边界：数据、有效标志、地址和标签在同一使能下保持对应关系；同沿接收旧输出与装载新输出不得混淆。用正常、阻塞恢复、复位中止等相关场景核对沿前事件与沿后状态，TB 的驱动/采样约定也写入记录。新增流水级、改变 RAM 读延迟或满时接收条件均须先回到架构审阅。

功能仿真与物理时序分别记录。存在目标频率时复用项目约束与 STA 流程，核对关键路径、未约束路径及例外；没有运行则明确未验证。不得用测试时钟频率或仿真 `--timing` 选项声称已满足频率。

按依赖从叶模块到子系统集成。先用合同中的可观察行为验证叶模块，再用实际顶层连接检查跨模块握手、顺序和复位中止。项目已有编译、lint 与自检仿真命令优先复用；以退出码和自检完成条件判断结果，超时或缺输入不能写成通过。若项目没有某类检查，明确未执行原因，不擅自引入大套工具链。

如果合同缺少实现必需的信息或实现需要改变接口/行为，先生成架构提案，说明原因并交由人审阅。不要先改 RTL 再静默修改架构以迁就代码。

交付给用户的代码说明应能从“这次改了哪条行为”落到受影响状态/端口、对应 RTL 和本次自检。优先选能检出错误的断言或对照，不用生成更多文档代替行为覆盖。更新条件、前递优先级和副作用按[时序方法](timing.md)核对；TB 层级引用失配与 DUT 断言失败分开报告，修复 TB 不得顺手改期望值迁就实现。

实现完成后再次运行 handoff 比较 modelHash。版本已变化则报告差异并停止宣称该代码符合最新合同。保存简洁实现记录，例如项目 implementation/ 下的 JSON：

```json
{
  "moduleId": "buffer",
  "modelHash": "来自本次 handoff 的真实值",
  "files": ["rtl/buffer.sv", "tb/tb_buffer.sv"],
  "verification": [
    {"command": "实际运行的命令", "status": "passed|failed|not_run|blocked", "detail": "实际结果或未执行原因"}
  ]
}
```

记录用于追溯，不能证明 RTL 一致性。未执行的验证必须明确记为 not_run。当前 tiny-stream 的 RTL 自检只覆盖其固定 fixture；packet-pipeline 只有架构示例，不能引用前者的仿真结果证明后者。

已有项目先核对 TB 版本和 ROM/golden 等输入。缺依赖标 blocked，不用编译成功替代仿真；不擅造验证资产。handoff 的 sourceDigest/evidence 是该版本的来源声明，运行 `rtlarch evidence` 核对已声明来源，并按 [证据与交付](delivery.md) 为本次验证绑定实际输入和结果。检查不能自动发现未声明依赖，预期源码变更仍需解释；关键结果保存在 clean 不删除的目录。

需要持久保存方案预算、执行本次验证或继续前一会话时，按 [持续工作](workbench.md) 使用 study / verify / resume。计算下界、当前输入下的实际运行、历史日志和人工批准分别报告。
