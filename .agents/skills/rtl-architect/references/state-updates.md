# 把状态更新解释接到源码和验证

当用户问“为什么停顿”“这个寄存器什么时候改变”，或 Agent 要设计/实现关键状态时使用。先选影响一笔事务的少量状态，从真实过程核对更新条件、右值、优先级与保持，再决定是否写入结构化规则。纯阅读文字整理不夹带这类语义修改。

## 表达范围

`localSignals[].driver` 保留旧 `kind=register / inputs / sourceText`，可选增加 `update`。旧输入集合不会自动变成规则；不从 enable、flush、valid 等名字猜行为。当前规则只表达整向量、单有效沿、同步优先级更新：

```json
{
  "reset": {
    "signal": {"moduleId":"top","interfaceId":"rst_n"},
    "activeLevel":"low",
    "value":{"kind":"constant","width":8,"value":"0"}
  },
  "branches": [{
    "id":"load",
    "condition":{"kind":"endpoint","endpoint":{"moduleId":"top","interfaceId":"accept","local":true}},
    "value":{"kind":"endpoint","endpoint":{"moduleId":"top","interfaceId":"next_data","local":true}}
  }],
  "otherwise":"hold"
}
```

reset 明确为 null 表示这个状态没有复位分支；不能据此把整个模块的复位删除。非空复位目前要求与作用域同域同步、极性一致。复位最高优先级，其后 branches 按数组顺序，首次匹配生效，均未命中则保持。条件和右值使用有效沿前值；不同状态同步更新，不将上一个状态的沿后值代入下一个。

条件必须 1 位，复位/写入值与状态等宽。表达式使用同一 AST；端点默认 unsigned，需要 signed、扩展、截断、移位时按 [数值类型](expression-types.md) 明确转换。加减在本节点位宽取模；比较要求等宽同符号输入，结果为 1 位 unsigned。`inputs` 必须与全部规则读取的端点集合一致，隐式保持无需添加自身；显式读取旧值仍要列出。sourceText、证据行号和规则应相互核对，但工具不会解析 sourceText 证明等价。

多个独立 if、部分位写入、多个过程驱动、异步复位、数组存储或复杂 HDL 类型不能未经证明改写为这个优先级模板。表达不了时保留旧输入集合、partial 和具体缺口；不要补假复位、复制寄存级或把更新条件省掉。

## 与用户一起阅读

点击状态查看按优先级排列的更新表，点证据定位实际源码；“数据从哪里来”突出写入值路径，“什么时候更新”突出条件和复位。两种追踪默认展开两层，在上游状态停止，背景连接仍保留。条件装载/优先级更新的结构标签来自明确规则，不意味着识别了完整流水线、FIFO 或仲裁器。

选一个有意义的同时条件解释结果，例如取消与装载同拍；让用户决定需要深入的行为，避免强制测验。仅来源新鲜不等于行为通过，规则已声明也不等于已验证。

## 用同一规则检查实际 RTL

模块 `contract.obligations` 可声明 `{id,kind:"state_transition",localSignalId,description}`。现有 `checks` 命令共用模型生成有限监视器；映射项在原字段之外提供 `state`（被检查的真实寄存器名）和 `signals:[{endpoint,pin}]`，`interfaces` 可为空对象。查询 `schema checks` 获取完整格式。

映射使用同一 `instancePath` 下显式引脚，不猜名字；组合 AST 内联，不能拿 RTL 同名组合线替换模型表达式。局部状态可映射真实寄存器；被检查状态本身只通过 state 映射。暂不支持数组实例。外部输入、其他状态及实际时钟/复位映射都需核对。

监视器在声明的有效沿采样沿前输入，在相反时钟沿检查更新结果；TB 在有效沿之外驱动，在比较完成后结束。复位（若有）、未证明不可达的分支和默认保持需触发。工具仅对字面常量条件证明不可达：常量 0 分支、被前面常量 1 屏蔽的分支，以及存在常量 1 分支时的默认保持；其他情况仍要求激励。缺激励返回 coverage_incomplete，实际状态不符仍是运行失败；不能自行标记不可达来跳过检查。它不检查两次观察之间的全部瞬态，也不证明任意序列、形式等价或完整协议。

生成后使用 `verify` 的 `obligations` 检查，将 RTL、TB、配置、checks.sv/json 全部列入输入清单。`assurance` 读取当前结果；模型或检查器变化需重新生成，旧通过不能覆盖最新失败。运行在用户指定的验证范围内，不自动批准架构。

至少设计一个保持场景让“错误写入”和“正确保持”的结果不同；分支计数本身不足以揭露错误。对更新优先级选择同时成立且右值不同的场景。工具维护的 `check:state-updates` 用真实 Verilator 注入错误数据、保持、复位与优先级，并核对未触发、映射缺失和证据过期；用户项目无需照搬固定案例。

## 看覆盖，不只看 PASS

对关键竞争在 state_transition 中增加可选 `priorityPairs: [{higher:"cancel",lower:"load"}]`。名称对应 update.branches 的稳定 ID，higher 必须排在 lower 前面。只有 higher 实际被选中、lower 条件同时成立、两个右值均已知且不同，才命中该覆盖目标。两个分支各自执行过、同时写相同值均不够。未声明的竞争不算已覆盖，不需为所有分支机械添加配对。

`assurance` 及网页按目标列出已命中、未命中、常量证明不可达、证据未知；不可达附具体原因，不算触发次数。改变旧值的写入与实际观察到的变化仅作诊断计数，不能替代故障注入。规则未证明可达且未命中时，先分析激励和约束，不能直接判 RTL 错。assurance 的 nextSteps 与网页“下一步”按缺口给出建议；这不是约束求解或自动生成 TB。过期、失败的运行不套用缺激励建议。

运行前核对检查依据：as_built 规则通过只说明还原模型与实现在该场景一致。验收设计时，先保留由用户需求形成、经审阅的规则，用 requirementIds 关联需求，再生成检查器；不要为迎合实际 RTL 改期望。运行保存本地批准快照，事后批准不能提升旧结果。需求文字是否被规则准确表达仍需人工核对，不是工具自动证明。

从源码发现状态、与已保存规则做单步函数比较，按 [状态提取与比较](state-observation.md)。它与场景监视器互补；提取的观察结果不自动成为设计规则。
