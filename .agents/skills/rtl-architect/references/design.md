# 从需求建立可审阅架构

先确定设计边界与可检验的行为，再细化内部结构。用户只要求局部修改时保留无关模块和稳定 ID。

## 需求与未知项

整理会影响结构的约束：输入/输出与数据含义、处理规则、吞吐/延迟、容量、时钟/复位、背压、异常处理。把用户明确给出的约束和当前假设分清；无法从上下文确定的条件进入设计或模块 openQuestions，必要时向用户问最少的关键问题。

每项需求使用稳定 ID，关联承担职责的模块，并给出可执行的验收条件。验收应描述可观察结果，例如顺序、计数、允许的阻塞、复位后的行为；不要只写“功能正常”。

## 从顶层向下

先完成最小可审阅设计，再展开 JSON。较大设计先比较会改变硬件代价的方案：串行复用/并行、单缓冲/双缓冲、固定调度/弹性流控。沿同一最坏配置比较周期、II、峰值存储、端口、反馈路径和验证难度。推荐一种并说明何种条件会使推荐改变；简单局部修改不强做多方案。

1. 定义顶层职责、外部接口及可验证目标。
2. 根据职责划分子模块，解释划分理由；先明确父层边界，再补内部连接。
3. 为每个模块写参数、接口、合同、未决问题和验证计划。
4. 确认同一需求在端到端路径中的责任归属；不要把整个设计的验收条件无差别复制到每个模块。

拆分依据是职责与状态归属：运算负责变换，存储负责保存与访问，控制负责调度和完成条件。只有存在真实边界才拆模块；几行组合运算不必包装成子系统。解释拆分解决了什么问题，例如把可变延迟 RAM 访问与固定运算分开，或让仲裁拥有唯一队列读指针。不要只写“提高模块化”。

沿数据路径说明每一步产物，沿控制路径说明启动、接受、完成和中止的条件。明确每份状态的唯一所有者，避免两个模块同时决定计数、重试或完成。反馈要解释反馈什么、何时生效、如何避免重复处理。跨时钟域若工具不能表达，记录未表达结构并阻止误交接，不能把两域改成同一域。

## 用具体情景检查设计

按 [时序方法](timing.md) 定义接收沿、结果可见与消费沿，沿真实寄存/存储边界追踪数据和控制。先推导周期表，再填写合同；模块数量不能当作流水级数。涉及目标频率时另列约束和待测路径，算法需要几拍不能作为多周期路径例外的依据。

在填写合同之前推演正常处理、连续输入、下游阻塞、满/空同时读写、处理中复位。只选择与当前接口相关的情景。每次明确本周期接受了什么、谁保存未完成数据、何时允许覆盖、哪个事件使状态前进。

例如，一个**假设的**带 ready/valid 输出队列可以约定：“在上升沿 valid && ready 时接受数据；下游阻塞时队首数据与 valid 保持；复位丢弃队列中未输出数据。”这不是已有 RTL 的默认行为。若没有 ready，则必须描述允许的到达速率与来不及处理的实际行为。

容量应有依据：峰值产生速率、连续阻塞长度、已有在途数据。平均速率不能推出峰值缓冲深度；未知下游阻塞上限不能承诺永不溢出。性能估计注明前提和瓶颈，最终由对应配置的测量验证。`latencyMinCycles` 只是下界；`latencyCondition` 同时写明计时起止、可重叠程度及阻塞条件，未知不能写成确定的“零延迟”。

需求的验收应能驱动 TB：给定输入序列、扰动与完成条件，检查输出、顺序、守恒和禁止发生的行为。实现策略或资源取舍放 decisions.rationale，未解决的策略选择放 openQuestions；不把设计理由复制到每个模块合同。

subsystem 通过自身边界连接直属子模块。producer/consumer 在父层表示对外角色，进入内部后边界方向由工具反转。不要为画图复制模块或发明第二套连线数据。

## 行为合同

- 延迟：明确测量起止握手边沿、初始状态以及背压前提；无限背压下不能承诺有限最大延迟。
- 流控：明确何时接受输入，阻塞时保持哪些数据，满/空与同时读写如何处理。
- 复位：说明在途事务取消还是保留、输出/计数/状态如何恢复；默认域声明也需要核实。
- 不变量：写可检查的容量、顺序、守恒或稳定性条件。
- 验证计划：对应需求的正例、边界、背压、复位及明确失败的超时检查。

只使用当前 Schema 支持的字段和协议。协议能力不足时把限制说清楚，不把复杂协议简写成 rv 并声称等价。

## 把高风险约束提前算清

按实际设计选择下列推演，结果写回合同、requirements 和 decisions；详细表可作带 modelHash 的派生附件，不引入第二份权威 Spec。

| 约束 | 设计时要回答 | 最小有效证据 |
|---|---|---|
| 周期与吞吐 | 哪个接受沿到哪个消费沿；装载、处理、排空、迭代、切换哪些串行/重叠；II 被谁限制 | 带配置和停顿前提的公式及边界代入；重叠用调度说明，不能简单相加或取 max |
| 存储 | 位宽×深度×份数、有效期、bank/地址映射、每拍读写端口、读延迟及同址行为 | 含端口占用和数据/tag 的逐拍表；容量估算与器件映射分列，不只用总 bit 数推 BRAM 数 |
| 在途与流控 | 已发未返回、已返回未消费各有多少；停顿何时生效；同时入/出队、取消后谁回收信用 | 容量守恒；深度覆盖最坏在途量和约定阻塞。无限停顿须可反压或有定义的丢弃策略 |
| 数值 | 每级 signed/位宽、扩展、截断、舍入、饱和顺序、极值 | 与独立 Golden 对齐的数学量；负值、极值和临界舍入例。结合顺序不可因流水而悄悄改变 |
| 反馈与频率 | 哪条状态递推限制 II，寄存边界、组合归约和大扇出在哪里 | 先推依赖距离及可用拍数；按项目工具做局部综合/时序探索。加流水需重新推反馈、完成和取消 |
| 复位/取消 | 清哪些有效位，RAM 是否保留，旧返回能否污染新事务 | 同沿取消/写回优先级、epoch/tag 或排空规则；无未初始化消费、取消后无旧提交的不变量 |

把预算、推导值和实测分开，保留余量及最敏感的假设。参数化设计核对最小/最大值、非整除尾块、计数位宽和配置变化时的状态归属；只支持固定配置时写明，不伪造可配置能力。

优先验证最可能推翻方案的一个问题，例如 RAM 推断或反馈时序。可在隔离目录做小探针，不把探针当正式 RTL 实现或整机验收；按项目权限与工具约定运行。缺真实 I/O 约束时留下集成交接项，不能伪造延迟或多周期例外凑通过。

审阅按风险复核：需求能否映射到模块和测试；端口是否支撑调度；数据与控制是否同笔；状态/资源是否守恒；异常能否恢复；指标能否在声明条件下验证。发现问题给反例、影响和修正建议。结构检查与独立行为推演不能互相替代。

## 输出与修改

首份候选同步按 [框图阅读设计](diagram.md) 整理有证据的接口组并生成默认布局。覆盖所有交付层级；用顶层与最复杂子层样稿验证，再沿一笔事务讲解。布局改进不能代替缺失的 RTL 连接或业务证据。

新设计输出结构化模型；局部变更输出增量 Proposal。模型和提案只放在 proposals/，由工具预览与登记。使用工具生成的 diff、issues 和 reviewUrl 向人说明结果；不另外维护一份与 IR 脱节的正式 Spec。

语义重命名保持 id，只改 name。一个需求变更涉及多个关联宽度或连接时，放进同一批命令统一校验。整架构替换适用于新方案，普通局部修改优先保留已有结构。

从现有 RTL 做优化时，先按 as-built.md 建立现状基线。优化后的行为与源码现状分别说明；未实测收益标为假设。参数修改须追踪实际实例覆盖、固定宽度及未传播参数，可用显式参数绑定进行受限整数求值和传播追踪，见 advanced-modeling.md；不自动提取或求值任意 HDL 表达式。

为主图命名端口组时说明设计用途和依据，保持原始端口映射。数据路径、请求、返回与写回分别可追踪；不要为了单向外观删反馈。职责、问题和验收条件按 [表达方式](writing.md) 写，避免复制工具术语与源码账本。
