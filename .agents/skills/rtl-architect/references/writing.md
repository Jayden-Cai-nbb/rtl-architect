# 写给需要判断设计的人

这些规则适用于 IR 的 name、职责、行为约定、需求、问题、分组说明以及交付报告。humanizer 在这里指表达自然、具体，便于理解；不改写事实，不弱化未知，也不增加口语花样。

## 先说发生什么

优先写“哪个模块，在什么条件下，做什么，产生什么结果”。专业名称保留，但先用一句话说明用途。参数名、信号名和精确数字只在帮助判断时出现。

| 避免的写法 | 更合适的写法 |
|---|---|
| 本模块实现数据通路的高效协同与控制闭环 | 收到读请求后读取 RAM，并把数据和对应地址返回处理单元。 |
| [源码事实][IR3] 控制逻辑执行事务状态耦合 | 复位会清空请求计数；RAM 内容保留。 |
| fidelity=partial，存在 REQUIRED_UNCONNECTED | CNU 的大部分元素连线还没导入，暂时不能用这份模型批准实现。 |
| 参数完成跨层级赋能与传播 | 顶层 ROM_FILE 传给存储模块的 INIT_FILE；未绑定的同名参数仍取各自默认值。 |
| 复位相关行为待进一步确认 | 未找到复位释放同步器。需要确认 rst_n 是否已在模块外同步释放。 |
| 通过完整校验，已达到高质量交付要求 | 本轮完成结构检查；ROM 数据缺失，功能仿真未运行。 |
| 流水线延迟2拍，高吞吐 | 空载、下游持续接收时，E0接收的输入在E2被下游接收；填充后每拍一笔。 |
| 所有状态随复位清零 | 复位采样沿清空计数和有效标志；RAM阵列不清零，原有事务取消。 |

不要凭写作示例填入项目事实。缺少“为什么”或“影响”的证据时明确不知道，不为了句子完整编造原因。

首次使用“拍”时说明哪一个时钟、哪个有效沿以及计时起止。需要解释时用事务A/B串起沿前事件和沿后状态，避免只有信号0/1或大量缩写；详细规则见 [时序方法](timing.md)。

## 每种内容各尽其用

**模块名称**用真实模块名或简短职责名；完整实例路径放路径字段/提示。不要把版本、状态、源文件名和长结论塞进 name。文件名 LLRmap.v 与模块名 llr_map 分开保留。

**模块职责**通常一至三句：接收什么、完成什么、交给谁。复位细节放 resetBehavior，验收放 verificationPlan；不要在所有字段粘贴同一段审计说明。

**行为约定**写可以实现和检查的条件。比如“下游未准备好时，输出数据保持到握手完成”；少用“合理处理、保证稳定、灵活支持”。已知限制写到对应行为旁边，避免堆到一个笼统免责声明里。

**问题**说明对象、现象、影响和下一步中的已知部分。例如“预算输入为10位，计数器只保留8位。需要确认超过255时应截断还是报错。”不要只写“位宽冲突待核实”，也不要替用户选答案。工具缺口、未导入连线、源码未知、缺少验证资产分别表述。

**分组名称**说明用途，例如“存储请求”“返回数据”“LLR配置”。它是阅读组织方式，描述中说明依据，不冒称 RTL 已有该总线或协议。不按信号名猜方向、数据/控制类型或复位语义。

**证据与版本**通过 evidence、targets、验证记录和版本信息承载。职责正文不逐句插源码行号、完整 hash、命令、工具状态或 `[事实]` 标签。解释争议时可在正文引用必要的信号名和证据链接。

## 交付报告够用即可

先给结论和链接，随后说明最值得审阅的变化及剩余问题。验证只写本轮实际执行；历史结果单独标明日期或批次。不把每条内部命令、每个阶段的进度汇报重新写一遍。

技术精度与可读性同时保留：正式字段如 latencyMinCycles、源路径、位域和 hash 保持准确；阅读正文用自然语言解释。没有新的问题就不加“风险提示”段，也不重复“不是证明”多次。篇幅随设计复杂度变化，不强制每次输出固定数量的标题或清单。
